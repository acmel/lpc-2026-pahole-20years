  • Where each inline lands, with its parameters

Alan Maguire, [PATCH v3 dwarves 0/9] Encoding of inline functions using BTF, 25 Sep 2026. With the inline feature, pahole encodes BTF_KIND_LOC_PROTO, PARAM and LOCSEC for inline functions during CU traversal, using libbpf location interfaces from the companion bpf series. pfunct --inline_sites shows each inline site: address, function+offset, section offset, and parameters with their location (register, address, constant); --elf uses vmlinux sections/arch info, --running uses kallsyms so kASLR is handled (needs privileges if kptr_restrict hides addresses). Check support with pahole --supported_btf_features (shows inline). Kbuild splits inline info into a separate split BTF object; pahole encodes it together, so one invocation. Output lines trimmed for the slide. Tie-in: inlining questions at the Cauldron talk were pointed here.

True signatures



/* source */
static int map_create(union bpf_attr *attr, bpfptr_t uattr);
/* as compiled */
static int map_create(union bpf_attr *attr, bool uattr__is_kernel);
  • BTF had source signatures; compilers change them
  • Mostly dead argument elimination
  • Kept only if DWARF locations match the ABI
  • x86_64: 875 of 69103 changed, 20 left out
  • Yonghong Song, pahole 1.32: +true_signature
Yonghong Song, pahole: Encode true signatures in kernel BTF; v8 cover letter 23 Jun 2026, merged upstream by Alan Maguire from the 25 Jun 2026 posting, released in pahole 1.32; enable with --btf_features=+true_signature (dd775208 detect aggregate ABI register usage, 5239db95 collect per-parameter information, e9629042 analyze per-parameter information; slide links the first). vmlinux BTF used source-level signatures; after optimization the real one can differ, so BPF programs written against the source signature could get wrong results, and users fell back to kprobes. Most changes are dead argument elimination; map_create shows a struct argument (bpfptr_t, a sockptr_t) reduced to one field, encoded as __. The new signature must follow the ABI by location, otherwise the function is left out: e.g. memblock_find_in_range, whose third parameter should be in RDX but DWARF says RSI+0. clang marks changed functions with DW_CC_nocall, but every function is checked. bpf-next numbers: x86_64 69103 functions, 875 changed, 20 left out; arm64 863 changed, 108 left out. Opt-in via --btf_features=+true_signature. Tie-in to the Cauldron talk: here pahole checks DWARF location lists against the ABI instead of trusting them.

Rust and other languages



struct Option<u32> {
    u32 __discriminant;      /*  0  4 */
    union {
        struct None {};
        struct Some { u32 __0; /*  4  4 */ };
    };                       /*  4  4 */
};
  • Rust enums: tagged unions, DW_TAG_variant_part
  • __discriminant from DW_AT_discr, not inferred
  • Mangled names: DECL_TAG, trace by plain name
  • Details: Extending BTF, eBPF track
Teaser for the eBPF track talk, Extending BTF to support more languages (Alan Maguire, Arnaldo). Rust kernel modules exist, BTF was designed around C. Rust enums with data are tagged unions; DWARF describes them with DW_TAG_variant_part / DW_TAG_variant / DW_AT_discr_value, tags C never used. pahole follows the shape LLVM already emits in BTF: a STRUCT wrapper with one anonymous UNION. The discriminant is located through DW_AT_discr (DWARF 5, 5.7.10) rather than inferred, since rustc layout is unstable, and named __discriminant because BTF needs names; it is only emitted when it does not overlap the payload (niche layouts like Option> emit nothing). Rust function tracing: kallsyms has mangled names, so pahole uses DW_AT_name and records DW_AT_linkage_name as a DECL_TAG, letting SEC(fentry/fmt) attach by the plain name (Alan PoC, linked). Open questions (variant kind, 128-bit discriminants, vtables) are for the eBPF track talk.
